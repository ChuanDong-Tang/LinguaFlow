# 账号系统改造计划

> 最终目标：OIO 完整拥有消费者账号系统，包括身份验证、身份绑定、会话、账号恢复、注销和安全审计；Authing 最终退出用户正常运行链路。第一阶段从邮箱验证码开始，整个迁移期间保证双轨可用、账号不重复、登录态不中断且每一步均可回滚。

## 当前状态

- OIO 已拥有用户、身份映射、Session、access/refresh token 及主要业务数据。
- Authing 当前仍负责邮箱/短信验证码认证、部分身份资料及相关账号操作。
- 腾讯云邮件服务已经开通，并已配置给 Authing 使用；OIO 尚未直接接入腾讯云邮件 API。
- 本计划不是一次性替换上线，而是按入口逐步迁移、逐阶段验收，最终解除 Authing 依赖。

## 一、改造原则

- OIO 的 `User`、`UserAuthIdentity`、`UserSession` 是账号与登录态的唯一事实来源。
- 腾讯云只负责投递邮件，不决定用户身份，也不签发登录 Token。
- 邮箱验证码由 OIO 服务端生成、保存和验证；验证成功后统一签发已有的 OIO access/refresh token。
- Authing 在兼容期继续服务尚未迁移的登录方式，但退出 OIO 邮箱验证码的正常链路。
- 不自动合并两个已有账号。发现身份冲突时停止绑定并进入明确的冲突处理流程。
- 所有改造必须可通过服务端开关灰度和回滚，不依赖重新发布 App。

## 二、第一阶段范围：OIO 邮箱验证码

### 用户流程

```text
输入邮箱
  → OIO 风控与频率检查
  → OIO 生成一次性验证码
  → 腾讯云发送邮件
  → 用户提交验证码
  → OIO 校验
  → 匹配或创建 OIO 用户
  → 绑定邮箱身份
  → 签发 OIO Session 与 Token
```

第一阶段覆盖：

- 邮箱验证码注册与登录合一。
- 已登录用户绑定或更换邮箱。
- 老 Authing 邮箱用户首次使用新入口时，无感关联原 OIO 账号。
- 重新发送、验证码过期、输入错误、频率受限等完整提示。
- iOS 邮件验证码自动填充所需的邮件内容与输入框配置。
- 登出、刷新 Token、撤销设备和账号删除继续使用现有 OIO 机制。

第一阶段不做：

- 密码登录与找回密码。
- 自动合并两个已经存在的 OIO 账号。
- 移除 Authing 代码或删除 Authing 用户数据。
- 改造短信验证码、Apple 或其他第三方登录。

## 三、身份匹配规则

邮箱进入认证流程前必须统一标准化：去除首尾空格、转换为小写，并沿用数据库唯一约束。

验证成功后的处理顺序：

1. 按标准化邮箱查找现有邮箱身份。
2. 找到身份时，登录其关联的 OIO 用户。
3. 未找到邮箱身份时，检查现有 OIO 用户资料及历史 Authing 身份能否唯一定位同一用户。
4. 能唯一定位时，将 OIO 邮箱身份绑定到原用户，不创建新用户。
5. 无匹配时才创建新的 OIO 用户。
6. 邮箱已属于另一个账号时返回账号冲突，禁止静默迁移或合并。

兼容期允许一个用户同时拥有：

```text
OIO User
├── email:<normalized-email>
├── authing:<authing-user-id>
├── phone:<e164-phone>       # 如已有
└── apple:<apple-subject>    # 如已有
```

## 四、验证码与安全要求

- 使用安全随机数生成一次性验证码，默认 6 位数字。
- 服务端只保存验证码哈希，不保存或记录明文验证码。
- 默认有效期 10 分钟；同一用途的新验证码签发后，旧验证码立即失效。
- 同一邮箱发送冷却时间默认 60 秒。
- 限制同一邮箱、IP、设备的小时与每日发送次数。
- 限制单个验证码的错误尝试次数，超过后立即作废。
- 请求发送接口的响应不能泄露邮箱是否已注册，避免账号枚举。
- 校验成功后一次性消费验证码，防止重放。
- 日志只记录脱敏邮箱、请求 ID、通道、耗时、结果及供应商错误码。

验证码状态优先存 Redis；若当前生产环境没有稳定 Redis，实施前需要确认替代存储和多实例一致性，不使用单进程内存作为生产方案。

## 五、腾讯云邮件接入

需要确认或补齐：

- 腾讯云邮件服务已开通。
- 发信域名及 DNS 验证完成。
- 发信地址、发信人名称可用。
- 验证码邮件模板已审核或满足发送要求。
- 生产环境凭证具备最小发送权限。
- 中国与美国常用邮箱的送达、延迟和垃圾邮件表现通过实测。

代码中已有腾讯云凭证用于其他服务，但邮件发送应使用独立配置项和最小权限；不得默认复用权限过大的通用密钥。

建议配置：

```text
OIO_EMAIL_OTP_ENABLED=false
OIO_EMAIL_OTP_ROLLOUT_PERCENT=0
AUTHING_EMAIL_FALLBACK_ENABLED=true

TENCENT_SES_SECRET_ID=
TENCENT_SES_SECRET_KEY=
TENCENT_SES_REGION=
TENCENT_SES_FROM_EMAIL=
TENCENT_SES_FROM_NAME=OIO
TENCENT_SES_TEMPLATE_ID=
```

具体名称以现有运行时配置规范为准；任何密钥不得提交到仓库。

## 六、Authing 双轨边界

OIO 邮箱入口启用后：

- 邮箱验证码的发送、验证、登录和 Token 刷新均不调用 Authing。
- App 启动及日常会话恢复不使用 Authing Token 查询用户资料。
- 现有 Authing 身份映射继续保留，用于老用户迁移、冲突核对和人工回滚。
- 短信及尚未迁移的第三方入口继续按现有方式使用 Authing。
- 单次邮件发送失败不自动偷偷切换 Authing，避免双验证码、绕过限流和不可控 MAU。
- 只有确认 OIO 邮件通道发生系统性故障后，管理员才可通过服务端开关整体回滚邮箱入口。

无论认证来自 OIO 还是 Authing，最终都必须换取同一种 OIO Session 和 Token，不保留两套业务登录态。

## 七、接口建议

接口名称在实现时结合现有路由规范确定，能力至少包括：

```text
POST /auth/email/code/send
POST /auth/email/code/verify
POST /account/email/code/send
POST /account/email/code/verify
```

请求需要携带用途，例如 `login`、`bind_email` 或 `change_email`；不同用途的验证码不可混用。

核心服务边界：

```text
EmailDeliveryProvider   # 只负责发送
VerificationCodeStore  # 保存、消费、限次
VerificationRiskGuard  # 邮箱/IP/设备限流
EmailIdentityService   # 匹配、创建、绑定、冲突处理
SessionTokenService    # 复用现有 OIO Token 能力
```

## 八、测试与验收

自动化测试至少覆盖：

- 新邮箱首次登录创建用户。
- 老 Authing 用户使用相同邮箱登录后仍进入原账号。
- 邮箱大小写和首尾空格不会产生重复用户。
- 已绑定邮箱直接登录。
- 邮箱冲突不会自动合并账号。
- 验证码过期、错误、超过尝试次数和重复使用。
- 重新发送后旧验证码失效。
- 邮箱、IP、设备维度限流。
- 腾讯云超时、拒绝、限流和异常响应。
- 登录成功后 access/refresh token 刷新正常。
- 关闭 OIO 邮箱开关后可恢复原 Authing 入口。

真机验收至少覆盖：

- QQ 邮箱、腾讯企业邮、Gmail、Outlook 和 iCloud 邮箱。
- 中国和美国网络环境。
- App 前后台切换、重新安装和换设备。
- 邮件延迟、重复点击发送、错误验证码和过期验证码。
- 已登录用户绑定邮箱与未登录用户邮箱登录。

## 九、完整阶段路线

### 阶段 0：建立可迁移的公共底座

目标：先解除业务代码与 Authing 的直接耦合，不改变用户当前体验。

实施内容：

- 建立统一的身份提供者、验证码投递、验证码存储和身份匹配边界。
- 明确 OIO 用户 ID 是所有业务数据的永久主键，禁止使用 Authing 用户 ID 作为业务主键。
- 盘点并导出 Authing 用户、邮箱、手机号、第三方身份及其与 OIO 用户的映射。
- 建立身份冲突报表，提前发现重复邮箱、重复手机号、孤立 Authing 身份和缺失映射。
- 为每种登录入口增加独立开关、灰度比例、指标和人工回滚能力。
- 验证现有 OIO Session 在不访问 Authing 的情况下可以启动、刷新和退出。

兼容办法：

- 所有用户继续走现有 Authing 登录入口。
- 新底座仅记录指标或影子判断，不改变认证结果。
- 发现映射异常时只记录，不自动修改用户数据。

完成条件：

- 业务用户与 Authing 身份映射可完整核对。
- 各入口能够独立切换，回滚不需要重新发布 App。
- App 日常会话不依赖 Authing Token。

### 阶段 1：接管邮箱验证码

目标：邮箱注册、登录、绑定和更换全部由 OIO 完成，腾讯云只负责投递。

实施内容即本文第二至第八节，建议上线顺序：

1. OIO 服务端直连已经开通的腾讯云邮件服务，功能开关保持关闭。
2. 在测试环境完成自动化测试和真实邮箱投递测试。
3. 生产环境先开放内部账号，再按小比例灰度。
4. 全量切换邮箱入口，观察至少一个完整计费周期。

兼容办法：

- 老用户按标准化邮箱关联现有 OIO 用户，并保留其 Authing 身份映射。
- 短信与第三方登录仍按原方式使用 Authing。
- OIO 邮箱发生系统性故障时，可整体回滚到 Authing 邮箱入口；不对单次失败做静默双发。
- 回滚只改变新的认证入口，不撤销已签发的 OIO Session。

完成条件：

- 正常邮箱链路完全不调用 Authing。
- 新老用户不会因切换入口产生重复账号。
- 验证码具备有效期、一次性消费、错误次数限制及多维限流。
- 自动化测试、中美网络及主流邮箱真机验收通过。
- 日志、监控和告警能够定位投递与验证失败原因。

### 阶段 2：接管短信验证码

目标：手机号注册、登录、绑定和更换由 OIO 完成，短信供应商只负责投递。

实施内容：

- 手机号统一转为 E.164 格式，并建立唯一身份约束。
- 按国家区号选择短信通道；第一版至少覆盖实际用户集中的中国大陆和美国。
- 复用阶段 1 的验证码存储、消费、限流、审计和身份冲突机制。
- 建立短信签名、模板、发送结果、供应商错误码和成本监控。
- 对短信轰炸、号码枚举、IP/设备批量发送和验证码暴力尝试增加专项限制。
- 支持未来增加第二家短信服务商，但业务代码不得绑定具体供应商。

兼容办法：

- 老 Authing 手机号首次通过 OIO 验证后绑定到原 OIO 用户，Authing 映射暂不删除。
- 手机号在两个 OIO 账号间冲突时停止登录或绑定，进入人工核验，不自动合并。
- 按国家区号和灰度比例切换；未开放地区继续走 Authing。
- OIO 短信通道故障时按地区整体回滚，不能同一次请求同时生成 OIO 与 Authing 验证码。
- 邮箱入口始终保持 OIO 可用，作为短信故障时的主要用户备用入口。

完成条件：

- 已开放地区的正常短信链路不调用 Authing。
- 中国和美国的发送成功率、延迟、成本及投诉率达到上线标准。
- 短信故障不会影响邮箱登录和已有 Session。
- Authing MAU 中不再包含仅使用邮箱或已迁移短信入口的用户。

### 阶段 3：接管第三方身份登录

目标：Apple 及产品实际保留的其他第三方登录由 OIO 直接验证，不再经 Authing 中转。

实施内容：

- 逐个盘点 Apple、微信、Google 等入口的真实使用量和保留价值，不使用的入口直接下线而非迁移。
- OIO 后端直接校验第三方签发的授权码或身份令牌，校验 issuer、audience、签名、有效期、nonce 等关键字段。
- 使用稳定的第三方主体 ID 作为身份键，不使用可能变化或隐藏的邮箱作为唯一匹配依据。
- 保存第三方身份与 OIO 用户的绑定关系，完善绑定、解绑和撤销授权流程。
- Apple 隐藏邮箱、邮箱变化及第三方不再返回邮箱时，仍能通过已绑定主体 ID 找到原账号。

兼容办法：

- 旧 Authing 第三方身份提前导出并映射到 OIO；无法可靠映射的用户在已登录状态下完成一次确认绑定。
- 同一个第三方主体 ID 只能属于一个 OIO 用户，冲突时禁止自动合并。
- 每个第三方入口独立灰度和回滚，邮箱、短信入口不受影响。
- 在全部活跃第三方用户迁移完成前保留 Authing 身份映射和旧回调配置。

完成条件：

- 所有保留的消费者第三方登录均由 OIO 直接验证。
- 老用户使用原第三方账号仍进入原 OIO 用户。
- 第三方授权撤销、换设备和隐藏邮箱场景通过验证。

### 阶段 4：接管完整账号生命周期

目标：除登录外，所有用户账号操作都由 OIO 独立完成。

实施内容：

- 邮箱/手机号绑定、更换、解绑及二次身份验证。
- 全设备列表、指定设备退出、全部设备退出和异常 Session 撤销。
- 账号恢复策略：优先用仍可访问的已验证身份，不依赖人工猜测用户归属。
- 账号注销、冷静期（如产品需要）、业务数据删除/匿名化及第三方身份解绑。
- 敏感操作安全通知、审计日志、后台最小权限和客服处理规范。
- 备份恢复、密钥轮换、验证码供应商故障和数据库故障演练。
- 明确不提供密码登录；若未来确有商业需求，作为单独安全项目评估，不夹带进验证码迁移。

兼容办法：

- 迁移期账号删除、更换身份等操作需要同时维护 Authing 遗留数据的一致性。
- OIO 操作成功但 Authing 清理失败时进入可重试任务，不回滚已经完成的 OIO 安全操作。
- 涉及身份冲突与账号恢复时采取保守策略，宁可暂停人工核验，也不自动串号。

完成条件：

- 新用户和已完成迁移的老用户，其完整生命周期无需调用 Authing。
- 删除、换绑、找回和 Session 撤销有自动化测试及审计记录。
- 客服和后台不再依赖 Authing 控制台处理日常账号问题。

### 阶段 5：停止 Authing 运行依赖

目标：Authing 从灾备供应商降为只读迁移档案，随后完全退出。

实施内容：

- 关闭所有用户端 Authing 登录、Token 刷新、用户资料查询和验证码调用。
- 停止向 Authing 创建或更新新用户，冻结双写。
- 完成最终用户、身份和必要审计数据导出，并验证导出数据可恢复、可查询。
- 连续观察至少一个完整登录周期，确认没有仍依赖 Authing 的活跃入口。
- 撤销 Authing 回调地址、Webhook、客户端密钥和 OIO 生产环境访问凭证。
- 根据合同、合规和备份策略删除 Authing 用户池数据并终止付费套餐。

兼容办法：

- 先停止运行调用但保留只读数据窗口，不立即删除 Authing 数据。
- 对长期未登录且无法自动迁移的老用户，重新登录时走 OIO 邮箱/短信验证和保守的原账号找回流程。
- 下线后不再以重新开启 Authing 作为常规回滚；灾备转为 OIO 自身备份恢复及可替换投递供应商。

完成条件：

- 生产环境连续一个完整周期无 Authing 用户认证调用。
- Authing MAU 降为零或仅剩经确认的非消费者用途。
- OIO 能独立完成注册、登录、绑定、恢复、会话管理和注销。
- 密钥、回调、Webhook、数据留存和合同均已完成收尾。

## 十、全阶段兼容规则

### 入口路由

迁移状态必须由服务端决定，客户端只展示服务端允许的入口。每个入口至少支持 `authing`、`oio`、`disabled` 三种状态，并可配置灰度范围或地区范围。

### 用户与身份

- 一个自然人可以绑定多种身份，但每个标准化邮箱、E.164 手机号和第三方主体 ID 只能属于一个 OIO 用户。
- Authing ID 在兼容期只是外部身份标识，不能成为新业务数据的关联主键。
- 自动迁移只允许确定性的一对一匹配；任何一对多、多对一或字段矛盾都进入冲突队列。
- 身份迁移成功不等于立即删除旧映射，旧映射保留到阶段 5。

### Session

- 所有入口最终只签发 OIO Session 和 Token。
- 切换、灰度或回滚认证提供者，不影响用户已有的有效 OIO Session。
- 只有明确的安全事件、账号删除或用户主动操作才能撤销既有 Session。

### 故障回滚

- 回滚以“入口 + 地区 + 新请求”为单位，不对单次失败静默跨系统重试。
- 已发送的验证码必须由原系统验证；切换系统后需重新获取验证码。
- 回滚开关、负责人、操作步骤、观察指标和恢复条件必须形成运行手册。

### 数据同步

- OIO 始终为主库；兼容期如需更新 Authing，仅作为遗留同步任务。
- 遗留同步失败不得覆盖或回滚 OIO 已确认的身份和安全状态。
- 所有迁移操作必须幂等、可重试并有审计记录。

## 十一、总体测试与监控

除各阶段专项测试外，每个阶段上线都必须回归：

- 新用户注册、老用户登录、换设备和重新安装。
- 邮箱、手机号、第三方身份交叉绑定及冲突。
- access/refresh token 刷新、过期、撤销和并发轮换。
- App 前后台、弱网、请求超时、重复提交和服务端重启。
- 中国和美国网络环境。
- 供应商限流、超时、部分故障及完全故障。
- 灰度切换、整体回滚和回滚后的再次切换。

统一监控至少包含：

- 各入口请求数、成功率、验证成功率和 P50/P95 延迟。
- 新建用户、迁移老用户、身份冲突和孤立身份数量。
- 邮件/短信供应商错误码、送达情况和单位成本。
- OIO 与 Authing 认证调用量及 Authing MAU 变化。
- Session 刷新失败、强制重新登录和账号恢复事件。

## 十二、最终完成定义

“自有账号系统”不等于 OIO 自己运营邮件或短信网络，而是：

- OIO 决定用户是谁、身份如何绑定及何时允许登录。
- OIO 生成并验证验证码，邮件和短信供应商仅负责投递且可替换。
- OIO 直接验证保留的第三方身份。
- OIO 独立签发、刷新和撤销 Session 与 Token。
- OIO 独立完成账号恢复、换绑、注销、安全审计和数据治理。
- Authing 不再处于用户注册、登录、日常会话或账号生命周期链路中。

达到以上状态并完成阶段 5 收尾后，账号系统改造计划才算全部完成。
