# 登录后账号偏好引导

> 状态：进行中
> 记录日期：2026-09-20

## 一、要解决的问题

当前首次体验被拆成了两个弹窗：

- 未登录时，在登录页上覆盖“选择界面语言”弹窗；
- 登录成功并进入主界面后，再覆盖“学习语言 + 学习难度”弹窗。

这套体验视觉上像临时配置，也让用户在已经进入产品后再次被打断。最新确定的首次体验是登录后、进入主界面前的四步账号引导。账号记录完成状态，重装不重复。

## 二、目标流程

```text
启动并登录 / 注册
  → 1/4 选择 App 语言
  → 2/4 选择要学习的语言
  → 3/4 选择学习难度
  → 4/4 选择从哪里知道 OIO
  → 写入 OIO 账户偏好和完成标记
  → 进入主界面，不再弹学习偏好窗口
```

四步都必须完成，不提供“跳过”。第二至第四步允许返回修改；每一步没有选择时，“继续”按钮不可用。它应当是独立的全屏引导页面，而不是在登录页或主界面上继续叠 `Modal`。

## 三、四步内容

### 1. App 语言

沿用当前支持的四种界面语言：

- 简体中文
- 繁體中文
- English
- 日本語

语言名称始终使用自身语言显示。登录页先使用设备或已保存语言；选择后界面立即切换，后续三步使用该语言；返回本页重新选择时也即时切换。

### 2. 学习语言

沿用当前 OIO 实际支持的学习语言选项。第一版保持与“我 > 语言设置”一致，不在引导页创造一套独立枚举。

### 3. 学习难度

沿用当前的难度选项及服务端含义。选项文案需要解释它将影响改写、回复和练习内容，不能只显示内部等级名。

### 4. 从哪里知道 OIO

单选且必选，第一版固定为：

- YouTube
- 小红书
- 抖音
- App Store
- Google Play

第一版不擅自增加“其他”或“朋友推荐”。渠道是产品归因信息，不应混入可随时修改的学习偏好，也不应写入 Authing 自定义字段。

## 四、首次用户的判定

更新方案：这里的“第一次”定义为**该账号第一次完成引导**。先进入登录页，认证成功后从服务端偏好读取 `guideState.account_onboarding_v1`；该标记是完成与否的权威数据。本地草稿必须按用户 ID 隔离。

判定规则：

1. 既有账号：上线前用数据迁移补齐已完成标记，不强制补做；
2. 新账号登录后若无标记：展示四步引导，中断后在该账号下恢复；
3. 已完成账号重新登录、卸载重装或更换设备：服务端标记仍在，不重复展示；
4. 读取服务端偏好失败：不能据此误判为新账号，保持可重试；
5. 更新偏好失败：留在最后一步允许重试，不能只写本地“完成”。

原本安装态判断和未登录全局草稿不再参与引导决策；模拟器可以用新账号／完成账号分别测试，重装只改变本地状态，不改变账号状态。迁移必须在新 App 上线前完成。

## 五、本地保存与登录后同步

登录后为当前用户建立一个带版本的本地草稿，例如：

```ts
type PreLoginOnboardingDraftV1 = {
  appLocale: AppLocale;
  learningLanguage: LearningLanguage;
  promptDifficulty: PromptDifficulty;
  acquisitionSource: "youtube" | "xiaohongshu" | "douyin" | "app_store" | "google_play";
  completedAt: string;
};
```

保存规则：

- 每一步选择即时保存到以账户 ID 为键的本地草稿，App 中断后可以回到未完成的步骤；
- 四步都完成且服务端保存成功后才写账号完成标记并进入主界面；
- App 语言继续写入现有 i18n 本地 Key，保证登录页立即使用所选语言；
- 登录后获取账户偏好，再展示并保存草稿；最后一步写入服务端成功后才进入 App；
- 网络失败不能当作已完成，保留当前步骤并允许重试；
- 同步成功后，服务端返回值重新落回本地，避免本地与云端长期分叉。

### 登录后的覆盖规则

用户刚刚在本次引导中主动完成的 App 语言、学习语言和难度，视为最新明确选择，登录后更新到该账户。若没有本次待同步草稿（普通登录、恢复 Session），则以服务端账户偏好为准并回写本地。

来源渠道建议采用“首次有效值”规则：账户尚无来源时写入；账户已有来源时不被重装或换设备覆盖。这样既满足新用户归因，也不会让老账号重复安装后污染来源数据。

## 六、服务端与数据设计

当前 `UserPreference` 已包含：

- `appLocale`
- `learningLanguage`
- `promptDifficulty`
- `guideState`

但当前没有来源渠道字段。第一版把单个首次来源作为 `UserPreference` 的可空字段保存，不塞进 `guideState` 或 Authing：

```text
acquisitionSource
```

服务端接口需要保证：

- 来源枚举严格校验；
- 普通用户只能在字段为空时写入首次来源，重复请求返回现有值；
- 偏好与来源的同步可安全重试；
- 管理后台后续可以按渠道查看注册或活跃用户，但首期不要求制作统计页面。

第一版复用 `/me/preferences`，并在 Repository 层保证字段为空时才接受首次来源。若未来需要多触点归因、投放活动或渠道变更历史，再迁移到独立归因模型。

## 七、与现有流程的合并

实施时需要：

- 用新的全屏四步流程替换 `UiLocaleSetupModal`；
- 把 `LearningPreferenceModal` 中的学习语言与难度合并到登录后的四步引导；
- 登录成功后根据账号完成标记决定是否显示四步，不再显示 `GUIDE_FIRST_LEARNING_SETUP` 弹窗；
- 保留“我 > 语言设置”，用户登录后仍可修改界面语言、学习语言和难度；
- 来源渠道不放入普通语言设置；如将来需要更正，应由独立入口或后台操作完成；
- 与账号系统改造保持解耦：无论登录最终来自 Authing 还是 OIO 自建认证，同步目标都必须是 OIO 用户 ID。

## 八、兼容和异常边界

- 用户在第 2～4 步杀掉 App：下次从未完成步骤继续，不丢前面选择；
- 用户在完成四步并成功写入服务器后杀掉 App：下次直接进入主界面；
- 登录失败或取消：不会进入四步引导；
- 登录成功但偏好读取或写入超时：不能误判为新账号或伪装完成，应留在可重试流程；
- 同一设备切换账号：只有当前引导产生的待同步草稿可写入一次，不能把上一个账号的普通本地缓存覆盖到下一个账号；
- 已完成账号重装后：服务器完成标记使其直接进入主界面，来源渠道保留账户原值；
- 老版本升级：必须先回填既有账号的服务端完成标记，再发布新客户端。

## 九、验收范围

### 自动化

- 新账号登录后依次完成四步，才能进入主界面；
- 每一步未选择时不能继续；
- 切换 App 语言后当前页和后续页立即换语言；
- 中途退出后恢复到正确步骤；
- 老账号、已完成账号、重装后已完成账号均不重复展示；
- 登录成功后偏好写入正确账户，来源只写首次值；
- 写入失败可重试，成功前不能进入主界面；
- 退出并登录另一个账号不会串写上一个账号的数据。

### 模拟器与真机

该改动涉及启动、登录、持久化和服务端同步，属于核心流程改动。Codex 完成自动检查后提供以下体验清单，由用户手动验证；除非用户明确要求代测，否则不主动启动模拟器、截图或执行视觉巡检：

1. iOS 当前最低支持系统；
2. iOS 最新系统；
3. Android 模拟器；
4. 国内 Android 与 Google Play 渠道配置各核对一次。

每轮只启动一套模拟器，避免并行运行造成 Mac 内存不足。必须覆盖新账号、既有账号、退出后换账号、重装、网络断开后恢复五条路径。模拟首次状态需使用未完成的测试账号，模拟已完成状态使用完成账号；卸载 App 不是重置账号引导的方法。

开发版模拟器还可在 React Native 开发菜单选择“预览当前账号的首次引导”，直接用已登录账号检查四步交互；这只是预览，不清除服务端完成标记。最后一步会真实保存当前账号的偏好和首次来源（来源已有值时保持原值）。真正规则仍须用新账号和已完成账号分别验证。

## 十、实施拆分建议

1. 确认四步视觉稿、难度说明文案及五个来源选项；
2. 建立本地 onboarding 状态机和兼容迁移；
3. 完成全屏四步 UI，并删除两个旧弹窗触发路径；
4. 增加来源归因数据结构、API 和迁移；
5. 接入登录成功后的幂等同步与重试；
6. 补齐自动化、模拟器和真实账户验收；
7. 验收通过后再决定随新包发布，不以 OTA 先行替代完整启动链路验证。

## 十一、第一版已确定

- 难度继续沿用“初级 / 进阶”两档，并在引导页补充面向用户的解释；
- 来源固定为 YouTube、小红书、抖音、App Store、Google Play，不增加跳过或其他；
- 来源首期只落库，不建设管理后台统计页；
- App 发布从功能开发中拆开，用户完成体验验收后再单独发起 OTA 或原生发布流程。
